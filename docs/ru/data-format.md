# Формат данных

Документ описывает формат хранения на диске, который код реализует сейчас, версия 1: файлы в каталоге данных, таблицы SQLite, что хранится открыто, конверт записи, обёртки ключей, KDF и ключ устройства в OS keychain. Каждый пункт сверен с кодом 2026-10-20.

- Полный проект, включая ещё не реализованные части (синхронизация, командные vault, записи сессий, экспорт), — [storage-format.md](../storage-format.md). Где они расходятся, этот документ описывает код.
- Порядок байтов big-endian. `be32(x)` — 4-байтовая big-endian запись `x`, `be16(x)` — 2-байтовая. `‖` — конкатенация. Метки в кавычках, например `"shellpp/v1/kek"`, — байты ASCII без завершающего нуля. `b64u` — base64url без дополнения.
- Источники: `crates/core/src/store` (схема в `migrations/0001_initial.sql`), `crates/core/src/crypto`, `crates/sync-api/src/envelope.rs`, `crates/core/src/vault`, `crates/core/src/lock`, `crates/core/src/service/lock_ops.rs`, `crates/core/src/settings`, `apps/desktop/src/dirs.rs` и `apps/desktop/src/platform/keychain.rs`.

## 1. Каталог данных

| ОС | Каталог данных |
|---|---|
| Windows | `%LOCALAPPDATA%\shellpp\` (логи в `logs\`, временные файлы в `tmp\` внутри него) |
| macOS | `~/Library/Application Support/shellpp/` (логи в `~/Library/Logs/shellpp/`, временные файлы в `~/Library/Caches/shellpp/tmp/`) |
| Linux | `$XDG_DATA_HOME/shellpp/`, по умолчанию `~/.local/share/shellpp/` (логи в `$XDG_STATE_HOME/shellpp/logs/`, временные файлы в `$XDG_CACHE_HOME/shellpp/tmp/`) |

- `SHELLPP_DATA_DIR=<dir>` заменяет все три на `<dir>`, `<dir>/logs` и `<dir>/tmp`. Тестовые запуски (тестовая сборка или `SHELLPP_TEST=1`) без неё не стартуют, поэтому никогда не используют постоянный профиль. `--demo` и `--screenshots` работают во временном профиле.
- Unix: каталоги `0700`, файл базы `0600`. Windows: права профиля пользователя.

Файлы в каталоге данных:

| Путь | Содержимое |
|---|---|
| `shellpp.db` | база SQLite 3 (раздел 2) |
| `shellpp.db-wal`, `shellpp.db-shm` | журнал предзаписи SQLite и его индекс; часть базы |
| `shellpp.lock` | пустой. Запущенное приложение держит на нём исключительную файловую блокировку ОС; второй процесс ждёт до 3 секунд и завершается с ошибкой хранилища |
| `backups/shellpp-<UTC yyyymmddThhmmssZ>.db` | копия (`VACUUM INTO`) перед миграцией схемы, хранятся 3 последние. У схемы 1 миграций нет, поэтому копий пока не бывает |
| `shellpp.db.<UTC yyyymmddThhmmssZ>.old` с `-wal` и `-shm` | база, отложенная в архив действием «Начать с новым хранилищем» (раздел 6) |
| `shellpp.db.<UTC yyyymmddThhmmssZ>-failed.old` с `-wal` и `-shm` | новая база, отложенная в сторону, если «Начать с новым хранилищем» не смогло её создать (раздел 6); бывает редко |
| `logs/shellpp.log`, `shellpp.log.1` … `.4` | диагностический лог с ротацией по 5 МиБ, если каталог логов внутри каталога данных (Windows, `SHELLPP_DATA_DIR`). Без секретов, адресов, имён пользователей и путей |
| `tmp/` | временные файлы явных действий пользователя, очищается при запуске (пока туда никто не пишет) |

## 2. База SQLite

- Крейт `rusqlite` со встроенной SQLite. Настройки соединения: `journal_mode = WAL`, `foreign_keys = ON`, `secure_delete = ON`, `synchronous = FULL`, `journal_size_limit = 0`, ожидание блокировки 5 секунд.
- `PRAGMA user_version` — версия схемы: `1`. Более новая версия отклоняется без изменения файла; версия 0 с таблицами отклоняется как чужой файл.
- `PRAGMA wal_checkpoint(TRUNCATE)` выполняется после каждой смены ключевого материала (смена пароля, восстановление, перевыпуск recovery key, выключение «Запомнить на этом устройстве»), перед «Начать с новым хранилищем» и при выходе, чтобы заменённые и удалённые обёртки не оставались в WAL.

### 2.1 Таблицы (схема 1)

UUID — `BLOB` по 16 байт; метки времени — `TEXT` в RFC 3339 UTC с миллисекундами (`2026-10-20T15:30:05.123Z`); логические значения — `INTEGER` 0 или 1.

| Таблица | Колонки | Что пишет версия 1 |
|---|---|---|
| `meta` | `key TEXT PRIMARY KEY`, `value TEXT` | `db_id`, `device_id` (текст UUIDv7), `created_at` при первом запуске; `last_app_version` при каждом запуске; `unlock_lockout` (раздел 5). `account_user_id` и `account_server_url` зарезервированы для синхронизации |
| `local_auth` | `id INTEGER PRIMARY KEY CHECK (id = 1)`, `personal_vault_id BLOB`, `kdf TEXT`, `kdf_salt BLOB`, `kdf_email TEXT NULL`, `updated_at TEXT` | одна строка после первого запуска: JSON KDF (раздел 4.2), 16 случайных байт соли, `kdf_email` = `NULL` (аккаунта нет) |
| `vaults` | `vault_id BLOB PRIMARY KEY`, `kind` (`personal`, `team`), `status` (`active`, `archived`), `role` (`owner`, `editor`, `viewer` или `NULL`), `current_epoch INTEGER`, `bound INTEGER DEFAULT 0`, `created_at TEXT` | одна строка: личный vault, `active`, роль `NULL`, эпоха 1, `bound = 0` |
| `key_wraps` | `vault_id BLOB`, `epoch INTEGER`, `kind` (`kek`, `recovery`, `device`, `hpke`, `chain`), `sender_user_id BLOB NULL`, `hpke_enc BLOB NULL`, `wrap BLOB`; первичный ключ (`vault_id`, `epoch`, `kind`) | строки `kek`, `recovery` и, с «Запомнить на этом устройстве», `device` для текущей эпохи; строки `chain` только после ротации (раздел 4.4). `hpke` пока не используется |
| `records` | `record_id BLOB`, `vault_id BLOB`, `class INTEGER`, `revision INTEGER`, `synced_revision INTEGER DEFAULT 0`, `key_epoch INTEGER`, `tombstone INTEGER DEFAULT 0`, `tombstoned_at TEXT NULL`, `server_seq INTEGER NULL`, `envelope BLOB`, `base_envelope BLOB NULL`; первичный ключ (`vault_id`, `record_id`); уникальный индекс по `record_id`, индексы `records_by_class`, `records_pending` | по строке на запись (раздел 3) |
| `sync_state` | `vault_id`, `cursor`, `last_sync_at`, `last_error`, `resync_classes` | создана, пустая (синхронизации пока нет) |
| `server_account` | `id = 1`, `server_url`, `user_id`, `email`, `refresh_token`, `secrets_epoch`, `bound_at` | создана, пустая (синхронизации пока нет) |
| `local_settings` | `key TEXT PRIMARY KEY`, `value TEXT` (компактный JSON) | строка только для настройки, которую пользователь менял; нет строки — значение по умолчанию. Неизвестные ключи и некорректные значения при чтении игнорируются. Пример: `security.auto_lock_minutes` = `null` («никогда», по умолчанию), `5`, `15`, `30` или `60` (`1` по-прежнему принимается) |

### 2.2 Что хранится открыто

- Зашифровано: `records.envelope` (и `base_envelope`, в версии 1 всегда `NULL`) и `key_wraps.wrap`. Всё, что ввёл пользователь (label, адреса, имена пользователей, пароли, ключи, заметки, теги, структура групп), — внутри конверта.
- Открыто: все остальные колонки, в том числе параметры KDF, соль, id vault и записей, классы записей, ревизии, эпохи ключей, значения `meta`, счётчик попыток разблокировки и `local_settings` (настройки интерфейса: тема, раскладка, автоблокировка; никогда не секреты и не данные хостов).
- Это раскрывает метаданные: число записей по классам, сколько раз запись правилась (ревизия), время создания (id UUIDv7) и размеры с дополнением.

## 3. Записи

### 3.1 Строки

- Колонки `vault_id`, `record_id`, `class`, `revision`, `key_epoch` и `tombstone` — копии заголовка конверта (раздел 3.2), записываются в той же инструкции. Строка, у которой колонки расходятся с заголовком, при записи отклоняется, а при чтении считается повреждённой.
- Каждая запись запечатывает новый конверт с `revision + 1` (1 для новой записи) и новым nonce, в одной транзакции.
- В версии 1 vault никогда не привязан к аккаунту синхронизации (`bound = 0`), и ни одна запись не синхронизировалась (`synced_revision = 0`, `server_seq` = `NULL`), поэтому удаление удаляет строку; tombstone не пишутся. Для отмены удаления ядро держит удалённый payload в памяти 60 секунд; приложение предлагает Undo первые 5 секунд (UI 2.4) и записывает запись обратно под тем же id. Пока идёт это окно, на диск об удалённой записи ничего не пишется.
- Записи с неизвестной версией конверта, неизвестным `type` или более новым `v` payload сохраняются без изменений и никогда не перезаписываются; запись, не прошедшая проверку, исключается и считается повреждённой, но никогда не удаляется.

### 3.2 Конверт, версия 1

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | `version` = `0x01` |
| 1 | 1 | `class` (раздел 3.4) |
| 2 | 1 | `flags`: бит 0 = tombstone; биты 1–7 равны 0 |
| 3 | 1 | резерв, `0x00` |
| 4 | 16 | `vault_id` |
| 20 | 16 | `record_id` (UUIDv7) |
| 36 | 8 | `revision`, u64 ≥ 1 |
| 44 | 4 | `key_epoch`, u32 ≥ 1 |
| 48 | 24 | nonce, случайный для каждого шифрования |
| 72 | L + 16 | шифротекст ‖ тег 16 байт |

- Заголовок — байты `[0, 48)`. Общая длина = 88 + L, где L — длина открытого текста с дополнением, кратная 256, от 256 до 262 144; значит, конверт занимает от 344 до 262 232 байт.
- AEAD: XChaCha20-Poly1305 (крейт `chacha20poly1305`).
- Ключ: `record_key[v, e]` = HKDF-SHA256(`vault_key[v, e]`, info = `"shellpp/v1/record"` ‖ `vault_id` (16) ‖ `be32(e)`).
- AAD: `"shellpp/v1/record"` (17 байт) ‖ байты заголовка `[0, 48)`, всего 65 байт. Шифротекст, перенесённый в другую запись, vault, ревизию или эпоху, не расшифруется.
- Дополнение: P ‖ `0x80` ‖ `0x00`… до L = 256 × ceil((len(P) + 1) / 256). Наибольший payload P — 262 143 байта.

### 3.3 Payload

Открытый текст P — компактный JSON в UTF-8:

```json
{"v":1,"type":"host","hlc":"0199f6a1b2c30001","device_id":"0199f6a1-b2c3-7d4e-8f00-112233445566","data":{}}
```

| Поле | Значение |
|---|---|
| `v` | версия payload этого типа; пока у всех типов `1` |
| `type` | имя типа (раздел 3.4) |
| `hlc` | гибридные логические часы последнего изменения, 16 строчных шестнадцатеричных цифр |
| `device_id` | устройство последнего изменения |
| `data` | поля типа ([data-model.md](../data-model.md)); в tombstone отсутствует |
| `deleted` | `true` только в tombstone |

### 3.4 Классы и типы

Класс — открытый байт по смещению 1; точный тип есть только внутри payload. Коды `0x00` и `0x0B`–`0xFF` зарезервированы.

| Класс | Код | Типы, которые код читает и пишет (код типа) |
|---|---|---|
| `vault` | `0x01` | `vault_meta` (`0x0101`, `{"name": "Personal", "color": "graphite"}` при первом запуске), `recovery_key` (`0x0104`, раздел 4.5), `device_info` (`0x0106`: `device_id`, `name`, `platform`, `app_version`) |
| `hosts` | `0x02` | `host` (`0x0201`), `group` (`0x0202`) |
| `keys` | `0x03` | `key` (`0x0301`), `identity` (`0x0302`) |
| `history` | `0x06` | `history_entry` (`0x0601`), расшифровывается при первом обращении |
| `connection_log` | `0x07` | `connection_log_entry` (`0x0701`), расшифровывается при первом обращении |
| `known_hosts` | `0x08` | `known_host` (`0x0801`) |

`snippets` (`0x04`), `forwarding` (`0x05`), `appearance` (`0x09`) и `workspaces` (`0x0A`) определены, но пока не пишутся.

## 4. Ключи

### 4.1 Цепочка ключей

```text
master password ─NFC, UTF-8─► Argon2id(argon2_salt, kdf params) ─► master_key (32 B, memory only)
master_key ─HKDF "shellpp/v1/kek"─► kek ─opens─► key_wraps (personal, e, kek) ─► vault_key[personal, e]
device_key (OS keychain) ─HKDF "shellpp/v1/device-wrap" ‖ db_id─► device_wrap_key ─opens─► (personal, e, device)
recovery_key ─HKDF "shellpp/v1/recovery-kek"─► recovery_kek ─opens─► (personal, e, recovery)
vault_key[v, e] ─HKDF "shellpp/v1/record" ‖ vault_id ‖ be32(e)─► record_key[v, e] ─► envelopes
```

- HKDF — HKDF-SHA256 с пустой солью, `info` = метка ‖ контекст и выходом 32 байта.
- `vault_key[personal, 1]` — 32 случайных байта из CSPRNG ОС, создаётся при первом запуске.
- Проверочного значения пароля на диске нет: пароль подтверждается успешным AEAD-разворачиванием строки `kek`.

### 4.2 KDF

`local_auth.kdf` хранит компактный JSON с полями в таком порядке:

```json
{"alg":"argon2id","v":1,"m_kib":65536,"t":3,"p":4}
```

| Параметр | Значение |
|---|---|
| Алгоритм | Argon2id, версия 0x13 (крейт `argon2`), без secret и associated data, выход 32 байта |
| Пресет десктопа | `m_kib = 65536` (64 МиБ), `t = 3`, `p = 4`; пресет мобильных `32768 / 4 / 2` |
| Допустимые значения | `alg = argon2id`, `v = 1`, `m_kib ≥ 32768`, `t ≥ 3`, `m_kib × t ≥ 131072`, `1 ≤ p ≤ 16`; десктоп `m_kib ≤ 1048576`, мобильные `m_kib ≤ 262144`, `t ≤ 16`. Всё остальное отклоняется до запуска Argon2id |
| Соль Argon2id | `argon2_salt` = SHA-256(`"shellpp/v1/kdf-salt"` ‖ `be16(len(e))` ‖ `e` ‖ `kdf_salt`), где `e` — UTF-8 от `local_auth.kdf_email`, пустая строка при `NULL` (в версии 1 всегда) |
| `kdf_salt` | 16 случайных байт, новые при первом запуске и при каждой смене пароля |
| Пароль | UTF-8 пароля после нормализации NFC, без обрезки пробелов; не меньше 8 скалярных значений Unicode после NFC, без требований к составу (D29) |

### 4.3 Обёртка (wrap blob), версия 1

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | `version` = `0x01` |
| 1 | 24 | nonce, случайный |
| 25 | n + 16 | шифротекст ‖ тег (XChaCha20-Poly1305) |

Обёрнутый 32-байтовый ключ занимает 73 байта.

### 4.4 Строки `key_wraps`

| `kind` | Что обёрнуто | Чем обёрнуто | AAD |
|---|---|---|---|
| `kek` | `vault_key[v, e]` | `kek` | `"shellpp/v1/wrap/kek"` ‖ `vault_id` ‖ `be32(e)` |
| `recovery` | `vault_key[v, e]` | `recovery_kek` | `"shellpp/v1/wrap/recovery"` ‖ `vault_id` ‖ `be32(e)` |
| `device` | `vault_key[v, e]` | `device_wrap_key` | `"shellpp/v1/wrap/device"` ‖ `vault_id` ‖ `be32(e)` |
| `chain` | `vault_key[v, e − 1]` | `chain_key[v, e]` = HKDF(`vault_key[v, e]`, `"shellpp/v1/epoch-chain"` ‖ `vault_id` ‖ `be32(e)`) | `"shellpp/v1/wrap/epoch-chain"` ‖ `vault_id` ‖ `be32(e − 1)` |

- `epoch` — эпоха обёрнутого ключа, кроме `chain`, где это более новая эпоха `e`.
- Строки `kek`, `recovery` и `device` есть только для `vaults.current_epoch`.
- Ротация личного vault (восстановление по recovery key или перевыпуск recovery key) в одной транзакции добавляет эпоху `e + 1` с новым случайным ключом, её строку `chain` и новые строки `kek`, `recovery` и (если ключ запомнен) `device`, а строки эпохи `e` удаляет. Затем записи перезапечатываются ключом новой эпохи. Интерфейс этапа 1 не предлагает ни одной из этих операций, поэтому у базы версии 1 обычно эпоха 1 и нет строк `chain`.

### 4.5 Recovery key

- 32 случайных байта, создаются при первом запуске. В локальном режиме приложение его никогда не показывает (D29), поэтому восстановить забытый пароль с ним нельзя.
- Хранится дважды: как обёртка `recovery` (раздел 4.4) и внутри зашифрованной записи `recovery_key`, `data` = `{"recovery_key": b64u(32 байта), "issued_at": метка времени}`. Текстовая форма, которую покажут с аккаунтом синхронизации, — `RK1-` и 11 групп по 5 символов Crockford base32 (32 байта и первые 2 байта их SHA-256).

### 4.6 Ключ устройства в OS keychain

| Параметр | Значение |
|---|---|
| Когда пишется | «Запомнить на этом устройстве» включено: по умолчанию при первом запуске (D29) или при включении в настройках |
| Service | `shellpp` |
| Account | `device-key:<db_id>`, `db_id` из `meta` текстом UUID в нижнем регистре с дефисами |
| Секрет | `device_key`, 32 случайных байта, хранится как b64u (43 символа) |
| Применение | `device_wrap_key` = HKDF(`device_key`, `"shellpp/v1/device-wrap"` ‖ `db_id` (16 байт)) открывает строку `device` при запуске |
| Когда удаляется | при выключении опции: сначала элемент keychain, затем строка `device` (и checkpoint WAL). Если ОС не даёт удалить элемент, ничего не меняется: опция остаётся включённой, а настройки сообщают об ошибке. «Начать с новым хранилищем» элемент оставляет: он открывает только архивный файл |

- Приложение один раз читает account `availability-probe`, чтобы проверить, что keychain работает; этот account никогда не пишется. Неподписанные сборки для macOS keychain не используют вообще.
- Тесты, `--demo` и `--screenshots` используют хранилище секретов в памяти и никогда не трогают OS keychain. В тестовом запуске (`cfg(test)` или `SHELLPP_TEST=1`) адаптер OS keychain к тому же сам сообщает, что недоступен, и не обращается к ОС.
- Windows: crate `keyring` пишет generic credential с `CRED_PERSIST_ENTERPRISE`. С перемещаемым профилем (Credential Roaming в домене) элемент переезжает на другие машины, куда входит пользователь, и копия `shellpp.db` там тоже открывается без мастер-пароля. В остальных случаях, в том числе на Windows без перемещаемого профиля, у копии `shellpp.db` на другой машине нет элемента keychain, и ей нужен мастер-пароль (`docs/security.md`, RR8).

## 5. Счётчик попыток разблокировки

`meta.unlock_lockout` хранит открытый JSON; он пишется в начале каждой попытки разблокировки (попытка считается неверной, пока пароль не подтвердится) и сбрасывается в `{"failures":0}` успешной разблокировкой:

```json
{"failures":6,"retry_at_ms":1792510215000}
```

- `failures`: неверные мастер-пароли подряд. `retry_at_ms`: время конца текущей паузы в миллисекундах Unix; до пятой ошибки отсутствует.
- Пауза после n-й ошибки — 5 с × 2^(n − 5), не больше 300 с. Пока пауза идёт, ядро отклоняет `unlock` до запуска Argon2id. Каждая попытка засчитывается как ошибка в момент начала, под той же блокировкой, что и проверка, и снимается, когда пароль подтверждается, поэтому одновременные попытки не обходят лимит. Нечитаемое значение считается нулём ошибок; конец паузы дальше, чем позволяет счётчик, укорачивается.

## 6. Архив базы

«Начать с новым хранилищем» (UI 13.2) работает только в заблокированном состоянии. Ядро выполняет checkpoint и закрывает базу, не отпуская блокировку `shellpp.lock` (другой процесс не откроет каталог, пока новая база не создана), и переименовывает:

| До | После |
|---|---|
| `shellpp.db` | `shellpp.db.<UTC yyyymmddThhmmssZ>.old` |
| `shellpp.db-wal` | `shellpp.db.<UTC yyyymmddThhmmssZ>.old-wal` |
| `shellpp.db-shm` | `shellpp.db.<UTC yyyymmddThhmmssZ>.old-shm` |

- Если имя занято, перед `.old` добавляется `-2`, `-3` … до `-999`. Если переименование не удалось, уже сделанные переименования откатываются.
- Затем создаётся новая пустая `shellpp.db`, и приложение переходит к первому запуску. Ничего не удаляется; `backups/` и элемент keychain старого `db_id` остаются.
- Если новую базу создать не удалось, архив возвращается на место. Недосозданная новая база (с её файлами) тоже не удаляется: сначала она переименовывается в `shellpp.db.<UTC yyyymmddThhmmssZ>-failed.old` (если имя занято, перед `.old` добавляется `-2`, `-3` …).
- Архив — полноценная база в формате этого документа; она по-прежнему открывается своим мастер-паролем или, если её элемент keychain ещё есть, при запуске без него. Чтобы вернуться к ней, закройте приложение, уберите текущие `shellpp.db` с файлами `-wal` и `-shm` и переименуйте архив и его файлы обратно в `shellpp.db`, `shellpp.db-wal` и `shellpp.db-shm`.

## 7. Что меняется при событиях

| Событие | Изменения на диске |
|---|---|
| Первый запуск | id в `meta`, `local_auth`, строка личного vault в `vaults` (эпоха 1), строки `kek` и `recovery`, записи `vault_meta`, `recovery_key` и `device_info`; затем, с «Запомнить на этом устройстве» и при наличии OS keychain, элемент keychain и строка `device` |
| Разблокировка | успешная разблокировка сбрасывает `meta.unlock_lockout`; после обновления приложения запись `device_info` получает новую `app_version` |
| Неверный пароль | `meta.unlock_lockout`: пишется в начале попытки (до Argon2id) и сбрасывается, когда пароль подтверждается |
| Запись создана, изменена или удалена | затронутые строки `records` (удаление группы ещё и переносит её содержимое), в одной транзакции |
| Настройка изменена или сброшена | строка `local_settings` записана или удалена |
| Смена пароля | `local_auth` (новая `kdf_salt`, текущий пресет, `updated_at`) и строка `kek`; строки `recovery` и `device` не меняются |
| «Запомнить на этом устройстве» вкл/выкл | элемент keychain и строка `device`, записываются или удаляются вместе (выключение: сначала элемент, затем строка и checkpoint WAL) |
