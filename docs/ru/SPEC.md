# Проект: Shell++, self-hosted SSH-клиент

## Состав документации

- `docs/ui-behavior-spec.md`: поведение интерфейса, экран за экраном.

- `docs/decisions.md`: проектные решения, принятые перед этапом 0 и позже.

- `docs/ru/`: русские версии спецификаций.

## Цель
Кроссплатформенный SSH-клиент с функциональностью уровня коммерческих клиентов
(хосты, ключи, сниппеты, SFTP, port forwarding, синхронизация между устройствами),
но с другой моделью владения данными. Мотивация: в коммерческом клиенте мои
локальные данные стали недоступны, когда истекла чужая командная подписка.
Здесь такое должно быть невозможно by design.

## Clean room: обязательные правила
- Не использовать код, ресурсы, бинарники, декомпиляцию, сетевой протокол или
  формат хранения Termius. Не искать и не открывать их исходники или дампы.
- Не использовать название, логотип, иконки, фирменные цвета, иллюстрации
  и тексты интерфейса Termius.
- Единственный источник требований к интерфейсу: `docs/ui-behavior-spec.md`
  и `docs/design-system.md`. Не запрашивай и не используй скриншоты оригинала.
  Если описания не хватает, задай вопрос, а не додумывай по своим
  представлениям об оригинале.
- Зависимости только с permissive-лицензиями (MIT / Apache-2.0 / BSD / ISC /
  MPL-2.0, для шрифтов OFL; также Zlib / BSL-1.0 / Unicode-3.0 / CC0-1.0 /
  Unlicense / 0BSD / CDLA-Permissive-2.0 и public domain, например SQLite).
  Перед добавлением зависимости проверяй лицензию и записывай её
  в THIRD_PARTY_NOTICES.md. [решение]
- Системные компоненты, которые мы не поставляем (графические и оконные
  библиотеки ОС, glibc), считаются платформенными зависимостями.
  LGPL-библиотеки внутри AppImage перечисляются в THIRD_PARTY_NOTICES.md.
  GPL и AGPL в поставке клиента запрещены. [решение]
- Для dev-зависимостей, которые не попадают в поставку (сборка, линтеры
  и тесты), дополнительно разрешены BlueOak-1.0.0 и CC-BY-4.0. CI проверяет
  лицензии через cargo-deny. [решение]

## Принципы (не обсуждаются)
1. Local-first. Приложение полностью работает офлайн, без аккаунта и сервера.
   Синхронизация опциональна.
2. Никаких проверок лицензии и подписки, триалов, тарифов, телеметрии,
   phone-home и удалённого отключения функций.
3. Данные пользователя всегда читаемы локально. Если отозван доступ к общему
   vault, удалён аккаунт, выполнен выход или сервер недоступен, локальная копия
   остаётся доступной и экспортируемой. Отзыв доступа прекращает только БУДУЩУЮ
   синхронизацию и никогда не стирает и не блокирует уже полученные данные
   удалённо.
4. Экспорт в открытые форматы в любой момент: JSON (документированная схема,
   открытый или зашифрованный), ~/.ssh/config, ключи в формате OpenSSH,
   known_hosts. Формат хранения описан в docs/.
5. Zero-knowledge sync. Сервер хранит только зашифрованные блобы и метаданные
   синхронизации. Ключи шифрования не покидают клиент в открытом виде.

## Стек по умолчанию
Если видишь причину что-то заменить, предложи это ДО начала работы.
- UI десктопа: GPUI Kit (крейт `gpui-kit`: GPUI из редактора Zed плюс
  библиотека gpui-component), нативный UI на Rust без webview. [решение]
- Терминал: alacritty_terminal (VT-парсер, сетка, scrollback) + собственный
  GPUI-элемент для отрисовки и ввода. [решение]
- SSH/SFTP: russh + russh-sftp, работа с ключами через ssh-key.
- Локальное хранилище: SQLite. Шифруется весь payload каждой записи;
  открытыми остаются только id записи, грубый тип, vault id, revision, эпоха
  ключа и служебные поля sync. Поиск и сортировка работают в памяти после
  разблокировки. [решение]
- Разблокировка мастер-паролем, опционально биометрией. По умолчанию в OS
  keychain ничего не хранится: только опция «биометрия / запомнить на этом
  устройстве» (по умолчанию выключена, с предупреждением) кладёт туда device key
  (crate keyring), которым vault key обёрнут дополнительно. Без OS keychain
  опция недоступна; запасного хранения в файле нет. [решение]
- Криптография: Argon2id (KDF), HKDF (разделение ключей), XChaCha20-Poly1305
  (данные), X25519 в HPKE (RFC 9180) в режиме Auth (обёртка ключей общих vault).
  Только проверенные крейты (RustCrypto, dalek); russh работает на бэкенде ring
  как явное исключение. Крейт `rsa` (advisory RUSTSEC-2023-0071) —
  задокументированное исключение: подпись выполняется локально, за апстримом
  следим. Никакой самописной криптографии. [решение]
- Иконки интерфейса: Lucide (ISC).
- Сервер синхронизации: Rust (axum) + PostgreSQL, SQLite для маленьких
  инсталляций. Docker-образ, docker-compose.yml, конфигурация через env.
- Монорепо:
  - apps/desktop: приложение на GPUI Kit (крейт `shellpp-desktop`) [решение]
  - crates/core: модель данных, шифрование, sync-клиент (переиспользуется на мобильных)
  - crates/ssh: SSH, SFTP, форвардинг, агент
  - crates/term-local: локальный PTY и serial-подключения (только desktop) [решение]
  - server/: сервер синхронизации
  - docs/: спецификации, архитектура, схема данных, формат хранения, протокол sync,
    threat model, решения [решение]
- Мобильный клиент (iOS/Android): отдельный UI, делается позже. Логика
  остаётся в crates/core и crates/ssh, которые не зависят от GPUI, поэтому
  архитектура ядра этому не мешает. [решение]

## Функциональность
Детали интерфейса для каждого пункта описаны в `docs/ui-behavior-spec.md`.

### Хосты
- Поля хоста: label, address, port, identity, группа, теги, заметки, цвет,
  startup snippet, переменные окружения, keepalive, кодировка, тема терминала,
  цепочка jump hosts (ProxyJump), proxy (HTTP/SOCKS), agent forwarding,
  дополнительные протоколы (Telnet, позже Mosh).
- Вложенные группы с наследованием настроек (username, identity, port, jump host).
- Identity: username + пароль и/или ключ, переиспользуется между хостами.
- Поиск и фильтр по тегам, quick connect по строке `user@host:port`,
  поиск по хостам и вкладкам (Ctrl+K).

### Keychain
- Генерация ключей Ed25519, ECDSA и RSA.
- Импорт ключей в форматах OpenSSH, PEM и PuTTY .ppk, поддержка passphrase.
- Сертификаты и FIDO2-ключи.
- Выгрузка публичного ключа на сервер (аналог ssh-copy-id).
- Работа с системным ssh-agent / Pageant и встроенный агент.
- Known hosts: TOFU с показом fingerprint при первом подключении, блокирующее
  предупреждение при смене ключа хоста, управление списком, импорт и экспорт.

### Терминал
- Вкладки, горизонтальные и вертикальные сплиты, переименование вкладок,
  авто-переподключение при обрыве, workspaces (сохранённые наборы вкладок).
- Цветовые темы (импорт схем iTerm2 и Windows Terminal), шрифт, размер,
  стиль курсора.
- Поиск по выводу, copy-on-select (опция), подтверждение многострочной вставки.
- Подсветка ключевых слов в выводе, включая пользовательские правила.
- Broadcast ввода в несколько сессий.
- История команд и запись сессии в лог (опции, см. раздел «Безопасность»).
- Локальный терминал и serial-подключения.

### Сниппеты
- Переменные `{{var}}`: при запуске появляется форма для ввода значений.
- Пакеты (папки) и теги.
- Запуск в текущей сессии или сразу на нескольких целевых хостах.

### Port forwarding
- Local, Remote и Dynamic (SOCKS5).
- Сохранённые правила, мастер создания, автозапуск при подключении,
  индикатор статуса.

### SFTP
- Двухпанельный менеджер: local ↔ remote и remote ↔ remote.
- Drag & drop, очередь передач с прогрессом, паузой и отменой.
- chmod, переименование, удаление, создание папок, скрытые файлы.
- Открытие файла во внешнем редакторе с автозагрузкой изменений обратно.

### Импорт
- ~/.ssh/config, включая Include, Host *, Match (хотя бы базово) и ProxyJump.
  Ключи из IdentityFile импортируются в Keychain. [решение]
- Сессии PuTTY из реестра Windows, CSV (колонки: label, address, port,
  username, group, tags), собственный JSON, known_hosts. Хэшированные записи
  known_hosts хранятся как есть; `@revoked` импортируются как запрещённые
  ключи, а `@cert-authority` пропускаются со счётчиком. [решение]
- Импорт идемпотентный: повторный запуск не создаёт дубликатов. Ключ —
  ключ источника (тип источника и Host alias, имя сессии PuTTY или UUID),
  а если его нет — (address, port, username); существующие записи
  не перезаписываются. [решение]

### Синхронизация и командный доступ
- Аккаунт на self-hosted сервере, URL сервера задаёт пользователь.
  Поддерживается несколько устройств.
- Цепочка ключей: мастер-пароль → Argon2id (случайная соль, привязанная
  к email аккаунта, параметры с версией) → master key → HKDF → два
  независимых ключа: KEK и auth key. Vault key генерируется случайно
  и хранится обёрнутым KEK. Каждая запись шифруется отдельно. На сервер
  уходит только auth key, сервер хранит его хэш; случайную соль и параметры
  KDF отдаёт pre-login эндпоинт (для несуществующего email —
  детерминированную фиктивную соль). Смена пароля переобёртывает vault key,
  атомарно обновляет auth key и соль и отзывает токены других
  устройств. [решение]
- Протокол:
  - pull/push изменений по курсору (серверный sequence number), курсор свой
    на каждый vault; [решение]
  - у записи есть UUIDv7, revision и tombstone для удалений;
    tombstone хранятся 90 дней, устройство с более старым курсором делает
    полную ресинхронизацию; [решение]
  - AAD связывает vault id, record id, тип, revision и эпоху ключа, поэтому
    подмена и перестановка блобов обнаруживаются; откат и удаление сервером
    не обнаруживаются; [решение]
  - push несёт `base_revision`; при расхождении сервер отказывает и отдаёт
    текущую версию; [решение]
  - конфликты решаются по last-writer-wins на уровне записи: победителя
    выбирают гибридные логические часы внутри записи, при равенстве — device id,
    удаление против правки решается тем же правилом. Проигравшая
    версия сохраняется отдельной записью-конфликтом в том же vault, видна
    на всех устройствах и разрешается вручную в UI. [решение]
- Пользователь выбирает, какие типы данных синхронизировать. История команд
  и журнал подключений по умолчанию не синхронизируются. Выбор задаётся на
  устройство, действует на push и pull, а выключение типа не удаляет его
  с сервера. Known hosts, workspaces, пользовательские темы и правила
  подсветки синхронизируются в личном vault (по умолчанию включены);
  настройки приложения остаются локальными; командные vault синхронизируются
  целиком. [решение]
- Журнал подключений всегда пишется в личный vault. В командном vault видны
  записи только тех участников, кто включил публикацию; это тип «только
  добавление», писать в который может и viewer. [решение]
- При входе в существующий аккаунт с устройства с локальными данными
  локальные записи перешифровываются под ключ аккаунта и сливаются
  с дедупликацией, как при импорте. [решение]
- Общие vault для команды:
  - единица шаринга — только vault: поделиться хостом или сниппетом значит
    переместить или скопировать его в командный vault, где запись
    перешифровывается и получает новый record id; [решение]
  - у пользователя пара ключей X25519, приватная часть которой синхронизируется
    внутри личного vault, и отдельный Ed25519-ключ SSH ID, публичная часть
    которого публикуется на сервер. Хост в командном vault может быть без
    credentials: каждый участник привязывает к нему свой SSH ID или identity,
    и эта привязка хранится в его личном vault; [решение]
  - vault key оборачивается публичным ключом каждого участника (HPKE, режим Auth);
    ключи участников закрепляются по TOFU, их отпечатки показываются
    для сверки вне сервера; [решение]
  - приглашение в два шага: ссылка содержит только одноразовый ID, owner
    подтверждает участника по отпечатку, и только после этого клиент owner'а
    оборачивает vault key; [решение]
  - роли owner, editor и viewer; их проверяет сервер при push, подписей
    записей в MVP нет. Любой участник, включая viewer, получает секреты
    vault. У vault может быть несколько owner; удаление аккаунта
    единственного owner'а блокируется, пока он не передаст
    владение; [решение]
  - при удалении участника vault key ротируется для оставшихся: начинается
    новая эпоха ключа, и клиент owner'а в фоне перешифровывает
    записи; [решение]
  - локальная копия удалённого участника НЕ стирается удалённо (принцип 3)
    и остаётся локальным архивом только для чтения, который можно
    экспортировать или скопировать в личный vault. [решение]
- Recovery key: 256 случайных бит, создаётся вместе с первым мастер-паролем,
  в том числе без аккаунта. Оборачивает личный vault key и даёт recovery auth
  key, которым можно задать новый пароль. В UI честное предупреждение: без
  пароля и recovery key данные восстановить невозможно. [решение]
- Сервер:
  - регистрация открытая или только по инвайтам (настраивается);
  - TOTP 2FA (сбрасывается только через admin CLI); [решение]
  - admin CLI;
  - health endpoint, rate limiting;
  - SMTP необязателен: без него приглашения работают только по ссылкам; [решение]
  - TLS через reverse proxy (пример конфигурации Caddy);
  - инструкция по бэкапу БД.

## Безопасность
- Секреты никогда не попадают в логи, в открытый текст на диске или в URL.
  Допустимые исключения — явные действия пользователя (открытый экспорт,
  экспорт лога в .txt, временные файлы SFTP), они показывают предупреждение;
  временные файлы удаляются при закрытии файла и при выходе. [решение]
- Мастер-пароль обязателен с первого запуска, даже без аккаунта, и потом
  становится паролем аккаунта. Сменить его можно и в локальном
  режиме. [решение]
- Автоблокировка по неактивности. Буфер обмена очищается после копирования
  пароля или ключа.
- Threat model в docs/security.md.
- Обязательные требования из `docs/ui-behavior-spec.md`:
  - 4.2: история не записывает ввод при запросе пароля, вычищает служебные
    последовательности и не предлагает похожие на секреты строки как сниппеты;
  - 7.3: приватный ключ скрыт по умолчанию и показывается только явной кнопкой;
  - 8.4: форвардинг по умолчанию слушает только 127.0.0.1;
  - 10.2: смена ключа хоста блокирует подключение до явного подтверждения;
  - 12.4 и 12.6: импорт истории с сервера (12.4) и запись вывода сессий (12.6)
    по умолчанию выключены.

## Производительность
Ориентиры, проверяются бенчмарком:
- старт меньше 1 с (от запуска до первого кадра главного окна);
- простой с 300 хостами меньше 150 МБ RSS (на Windows — working set);
- не больше 10 МБ на новую сессию;
- scrollback по умолчанию 10 000 строк.

## Качество
- Unit-тесты для crates/core: шифрование, merge при синхронизации,
  парсер ssh_config, фильтр секретов в истории.
- Интеграционные тесты SSH/SFTP/форвардинга против OpenSSH в Docker,
  в Linux-джобе CI; e2e на Windows используют тестовый SSH/SFTP-сервер
  на russh, который лежит в репозитории. [решение]
- E2E-тест синхронизации: два клиента + сервер.
- Тесты интерфейса по UI-спецификации (GPUI-тесты, см. «UI/UX»); элементы ищутся
  по id элемента, а не по тексту. [решение]
- Тесты и скрипт скриншотов работают с временной папкой данных
  (`SHELLPP_DATA_DIR`) и никогда не трогают постоянный профиль пользователя.
- Автотест контраста цветовых токенов.
- CI на GitHub Actions: clippy, rustfmt, тесты, сборка под Windows, macOS и Linux.

## Порядок работы
Работай строго по этапам. После каждого этапа: тесты зелёные, коммит,
краткий отчёт (что сделано, что осталось, какие есть риски). Дальше жди
моего подтверждения.

Элементы будущих этапов скрываются флагом этапа, а не показываются неактивными.
Исключение — каркас окна и боковая панель: вкладка SFTP и все шесть разделов
боковой панели видны всегда, а раздел, экран которого ещё не реализован,
открывает заглушку «In development». UI-тесты функции пишутся на том этапе, где
она реализуется, а отчёт каждого этапа перечисляет то, что ещё скрыто или
показано заглушкой. [решение]

Этапы 0–2 сначала были сделаны на Tauri + React; их UI переделывается на GPUI Kit
(`docs/decisions.md`, 27). [решение]

0. Дизайн-документы в docs/: архитектура, схема данных, формат хранения,
   протокол синхронизации, threat model (`docs/architecture.md`, `docs/data-model.md`,
   `docs/storage-format.md`, `docs/sync-protocol.md`, `docs/security.md`).
   Плюс тема и базовые компоненты по design-system.md в `apps/desktop`,
   со страницей-витриной. Тесты этапа: автотест контраста и тесты
   компонентов. Покажи до написания основного кода. [решение]
